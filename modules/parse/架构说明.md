# 解析模块（modules/parse）架构说明

## 1. 概述

`modules/parse` 是 Witt（原 TASoftware）的「数据解析」层，职责是把各类**原始数据**（自研 AA55 二进制帧、调试数据流、凯芯数据、RTCM 3.x 差分数据、CAN BLF 记录、通用分隔文本）统一转换成**结构化帧（`ParsedFrame`）或文本表（`TextFileTable`）**，并在此基础上提供查看、按帧导出 CSV、多文件时间对齐合并（New Code）与降采样等工具。

模块定位与上下层关系：

```
┌──────────────────────────────────────────────────────────────┐
│  UI 层：ParsePanel（数据解析面板）  ┌────────── 分析模块 analysis  │
│   协议按钮 / 输出 / 导出 / New Code / 降采样   │ compare/raw 消费   │
└──────────────┬───────────────────┘───────────┘
               │ ParserFactory / ParserBase（多态分发，唯一入口）
               ▼
┌──────────────────────────────────────────────────────────────┐
│  parser/ 解析核心                                            │
│  ├─ core/       协议定义 + 通用 AA55 帧解析 + RTCM/CAN 辅助    │
│  ├─ single/     注册表驱动的标准帧协议解析                     │
│  ├─ debugstream/ AG 0x51~0x56 / 614E-B 调试数据流             │
│  ├─ external/   凯芯（外部 Python + MEX）                      │
│  ├─ other/      RTCM 3.x（帧扫描 + RTKLIB 深解码）             │
│  └─ can/        CAN RTK（BLF → 0x1CEBFF9A）                   │
└──────────────────────────────────────────────────────────────┘
               输出：ParseResult（文本/CSV 内容 + 帧列表 + 状态）
```

下游消费方：
- `commtool/streamframer`：复用 `FrameParser` 的静态函数处理实时串口/TCP 流的粘包/半包；
- `commtool/realtimeparsepanel`：实时流按 `protocolRegistry` / DEBUG / 614E-B 协议解码；
- `analysis/`：`core/converter.h` 用 `protocoldefs.h`（`ParsedFrame`/`ProtocolID`）转统一数据集；`compare/` 用 `columnextract.h` 的 `TextFileTable` 加载真值/对比表；
- `simulator/`：其 `encoders/aa55encoder` 生成的 AA55 容器帧与本模块解析端一一对应（同一协议的两个方向）。

## 3. 统一入口与结果模型

### 3.1 ParseResult（统一产物）

```cpp
struct ParseResult {
    QString    displayText;      // 界面显示内容（大结果自动截断/头尾预览）
    QString    fullText;         // 完整文本（导出用）
    QString    infoText;         // 状态栏摘要（如 帧数/CRC错数、凯芯行数）
    ProtocolID protocolId;
    QList<ParsedFrame> frames;   // 帧类分支缓存（按帧导出用）
    QString    externalCsvPath;  // 外部脚本/进程生成的临时 CSV（凯芯）
};
```

### 3.2 ParserBase 基类

每个协议一个 `ParserBase` 子类，多态分发；`parseToResult(rawData, filePath)` 是唯一切入点，分为两类路径：

1. **默认实现（帧路径）**：`parse()` 扫描帧 → `formatFrame()` 逐帧格式化为 CSV 行或 `[#偏移] 文本` 行；`csvHeader()` 非空时按 CSV 输出，否则按原生文本输出；最后统计 `CRC错数` 写入 `infoText`。
2. **重写实现（外部/深解码路径）**：凯芯（调用 Python 脚本写临时 CSV）与 RTCM（RTKLIB 深解码为 RINEX 文本）重写此方法，不走帧列表。

CRC 开关：基类默认 `m_skipCrc = true`（界面「CRC校验」勾选框默认不勾 → 跳过校验），对使用非标准校验或不含 CRC 的文件友好。

### 3.3 ParserFactory

`createAll()` 统一创建：先为注册表每条 `ProtocolDescriptor` 生成一个 `FrameProtocolParser`，再追加 RTCM / CAN / DEBUG / 614E-B / 凯芯五个特殊解析器。面板按钮顺序即此顺序。

## 4. 协议定义与通用帧（core/）

### 4.1 protocoldefs.h

集中定义：`ProtocolID` 枚举、AA55 `FrameHeader`、**全部** payload 结构体、`ParsedFrame`（内部 `union` 挂 20 余种协议结构体）、RTCM 帧定义。

`ProtocolID` 一览（`resolveProtocolID(id, len)` 由帧 ID + payload 长度确定协议）：

| ID | 标签 | payload | 说明 |
|----|------|--------|------|
| 0x0002 | AHRS基本 | 44 B | 姿态 + IMU + 温度 |
| 0x0022 | AHRS扩展 | 49 B | 基本 + flag + status |
| 0x0023 | 四元数 | 53 B | 四元数 + IMU |
| 0x0156 | AG数据 | 50 B | 姿态/陀螺/加计 + RTK状态 |
| 0x0166/len94 | 组合导航(融合) | 94 B | 位置速度姿态融合结果 |
| 0x0166/len105 | 倾斜测量 | 105 B | 杆/激光/倾角数据 |
| 0x0146 | 激光 | 76 B | 激光点/杆坐标（原生文本非 CSV） |
| 0x0140 | 南方激光 | 73 B | 累加和校验 |
| 0x0446 | 中海达激光 | 82 B | 累加和校验 |
| 0x0168 | 姿态 | 36 B | 姿态 + 标准差 |
| 0x0199 | 614P-pro四元数 | 46 B | 累加和校验 |
| 0x0051~0x0056 | AG调试数据流 | 86/59/24/15/172/140 B | IMU/GPS/双天线RTK/轮速/KF/参数 |
| 0x0101/0x0111/0x0131 | 614E-B调试 | 51/71/208 B | IMU/GNSS/KF |
| 0x0109~0x0114 | 凯芯 | — | 外部 MEX 解析，综合 CSV |
| 0xCD01(内部) | 联试_CAN981 | 40 B | CAN ID=0x1CEBFF9A，5×8B |

同帧 ID 区分：0x0166 同时承载「组合导航」与「倾斜测量」，靠 payload 长度（94 / 105）区分。

### 4.2 AA55 通用帧（FrameParser）

标准帧容器（小端）：

```
┌──────────┬────────────┬──────────────┬──────────┬───────────────┐
│ AA 55    │ ID (u16 LE)│ Length (u16) │ Payload  │ CRC32 (u32 LE)│
│ 同步头2B │ 4~5 偏移   │ payload 长度  │  变长    │ 初始值=1      │
└──────────┴────────────┴──────────────┴──────────┴───────────────┘
```

- 帧头固定 6 B；总长 = 6 + payload + 4。
- `computeCrc32`：初值 `1`、多项式 `0xEDB88320`，覆盖「帧头 + payload」。
- `parseAll` 扫描流程：`findNextFrame`（AA 55）→ `isFrameComplete`（长度足够）→ 读 ID/长度 →（可选）CRC32 校验 → `resolveProtocolID` → `parsePayload` 解出 `ParsedFrame` → 前进到帧尾继续。
- 内置 `computeChecksum8`（累加和）：南方激光 0x0140 / 中海达激光 0x0446 / 614P-pro 四元数 0x0199 定义用累加和校验而非 CRC32，因此这类文件通常保持「跳过 CRC 校验」。

## 5. 标准帧协议（single/）：注册表驱动

`protocolRegistry()` 返回 `ProtocolDescriptor` 列表，一个描述符聚合一个协议的全部元信息：

```cpp
struct ProtocolDescriptor {
    QString label;                                   // 按钮标签
    ProtocolID pid;
    bool hasCrc;
    QString csvHeader;                               // 空 = 原生文本格式
    std::function<QList<ParsedFrame>(const QByteArray&, bool)> parseFn;
    std::function<QString(const ParsedFrame&)> formatFn;   // CSV 行/文本行
    QList<FieldDescriptor> fields;                   // 字段显示名 + 取值 lambda
};
```

`FrameProtocolParser` 只是描述符的薄封装，`parse/formatFrame/csvHeader` 全部转发给描述符。注册表同时是：

- **解析器来源**（工厂据此建按钮与解析器）；
- **CSV 表头与逐行格式来源**（导出用）；
- **字段列表来源**（`fieldsForProtocol()`，供列选择等 UI）。

除注册表 11 个标准帧协议外，CAN-RTK 也注册一份仅供字段/CSV 查询的描述符（解析走 `CanRtkParser`）。

## 6. 特殊解析器

| 解析器 | 按钮 | 输入/范围 | 方式 | 产物 |
|--------|------|----------|------|------|
| `DebugFrameParser` | AG调试数据流 | 0x51~0x56 | FrameParser 全扫后按范围过滤；界面只显示 0x51 主轴 | 按帧 ID 导出 6 个 CSV（`csvHeaderFor/formatFrameFor`） |
| `Eb614DebugParser` | 614E-B调试数据流 | 0x0101/0x0111/0x0131 | 同上 | 按帧 ID 导出 3 个 CSV |
| `KaixinFrameParser` | 611-AG调试数据流 | 0x0109~0x0114 | 检测文件头 `AA55 0901`；重写 `parseToResult`，调用外部 `scripts/kaixin_parse.py`（加载 `decode_kaixin.mexw64`） | 一份综合临时 CSV + `KaixinResult` 统计（有效行/GPS行/固定解行/版本等）；导出=拷贝 CSV |
| `RtcmFrameParser` | RTCM 3.x | 0xD3 帧流 | 两级：`RtcmParser` 帧级扫描（preamble 0xD3 + 10-bit 长度 + CRC-24Q）；`RtcmDeepDecoder` 用 RTKLIB `input_rtcm3()` 解为逐历元 `obsd_t` | 界面/导出为 RINEX 观测文本；`infoText` 统计历元数 |
| `CanRtkParser` | 联试_CAN981 | 仅 `.blf` | `CanBlfParser`：144B BLF 头 + zlib 解压（`qUncompress`）→ 扫描 CAN 扩展帧 0x1CEBFF9A → 每 5×8B 组一解算历元 → 大端解码 `CanRtkData` | 17 列 CSV（时间/定位/位置/速度/姿态+有效性） |

注意：凯芯按钮在主面板做了文件类型预检（BLF 只能走 CAN981；CAN981 只收 BLF），避免误用。

## 7. 解析面板（ParsePanel）与线程模型

界面结构：文件加载行（含「CRC校验」勾选、路径、状态摘要）→ 协议按钮行（互斥可勾选，代码动态生成）→ 输出文本框 → 导出 CSV / New Code / 降采样 / 清空。

主流程：

1. 加载文件到 `m_rawData`（`QByteArray` 快照，供后台线程复制）；
2. 点击协议按钮：互斥勾选 → 类型预检（BLF/凯芯等）→ 置忙禁用按钮，输出「解析中...」；
3. `QFutureWatcher<ParseResult>` + `QtConcurrent::run` 在**后台线程**执行 `doParse`（内部重新 `createAll` 建临时解析器 → `setSkipCrc` → `parseToResult`，多态分发，不识别具体协议类型）；
4. 完成后回到 UI 线程：写输出、状态摘要，缓存 `fullText / frames / externalCsvPath / protocolId` 供导出。

导出策略（按协议族分流）：

| 场景 | 行为 |
|------|------|
| 凯芯 | 直接拷贝缓存临时 CSV 到目标路径 |
| DEBUG | 选目录后按 0x51~0x56 导出 `debug_0x51_组合导航IMU.csv … debug_0x56_参数.csv` |
| 614E-B | 按 0x0101/0x0111/0x0131 导出 `614EB_0x0101_IMU.csv …` |
| RTCM | 导出深解码后的 RINEX 观测文本（.txt） |
| 其他 | 按协议描述符 `csvHeader`（或文本前缀启发式）判断存 .csv 还是 .txt |

## 8. 文本工具

### 8.1 columnextract（New Code）

- `TextFileTable`：一个文本表的统一模型（表头 + 字符串行 + 时间列数值），`loadTextFileTable()` 自动识别时间列。
- `ColumnExtractDialog`：加载**多个**空格/逗号/Tab 分隔文件 → 勾选要导出的列 → 指定主轴（默认取行数最少即低 Hz 文件）→ **按时间戳最近邻对齐合并**导出单一 CSV。
- 异步加载/导出（`QFutureWatcher`），数据清理移到后台线程避免 UI 卡顿；`analysis/compare` 也复用同一 `loadTextFileTable` 读真值/对比文件。

### 8.2 downsampledialog（降采样）

选 CSV/TXT → 预览前 50 行 → 用户指定**起始行（基准点）**与降采样倍数 → 从起始行起每隔 N 行取 1 行，异步写入新文件（预览、进度、取消、导出完成后提示）。

## 9. 扩展点

- **新增标准帧协议**：`protocoldefs.h` 加结构体 + 枚举值 → `FrameParser` 增加 `parseXxx` 并在 `parsePayload` switch 登记 → `protocolregistry.cpp` 增加一条 `ProtocolDescriptor`（CSV 表头、formatFn、fields）。按钮与解析器由工厂/注册表自动生成，无需改 UI。
- **新增特殊解析器**：继承 `ParserBase`（需要时重写 `parseToResult`），并在 `ParserFactory::createAll()` 登记一行；若涉及多 CSV 导出，在 `ParsePanel::onExportClicked` 增加分流。
- **新增协议字段/列**：只改对应协议的 `fields` 与 CSV 表头即可联动显示与导出。
